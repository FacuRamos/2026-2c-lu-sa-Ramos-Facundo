🏛️ Justificación Arquitectónica: ¿Por qué WebSockets en lugar de HTTP Polling?

En una aplicación móvil de ticketing y eventos en vivo, la inmediatez y la eficiencia de recursos son factores críticos de calidad de software (ISO/IEC 25010). A continuación se detalla la comparativa técnica que fundamenta nuestra decisión de diseño:

Criterio Técnico HTTP Polling Tradicional (Sondeo periódico) WebSockets Full-Duplex (Nuestra Arquitectura)
Protocolo y Handshake ✕ Ineficiente Recrea petición HTTP Request/Response cada 2 o 3 segundos. Requiere revalidación TLS y procesamiento repetido. ✓ Óptimo Único handshake inicial mediante Upgrade: websocket (HTTP 101 Switching Protocols, RFC 6455). La conexión TCP queda viva y abierta.
Overhead por Mensaje ✕ ~500 - 1.000 bytes por sondeo en cabeceras HTTP (Host, User-Agent, Authorization: Bearer JWT, Accept), aun cuando no hay mensajes nuevos (304 / 200 []). ✓ 2 a 10 bytes de sobrecarga de trama (frame header + masking). Reduce en más de un 95% el consumo de ancho de banda celular.
Latencia de Entrega ✕ 1.5s - 3.0s (Latencia promedio = Intervalo de Polling / 2). No ofrece sensación de conversación instantánea en vivo. ✓ < 50 ms (Server-Push) El servidor empuja el frame de forma reactiva al receptor tan pronto como el mensaje es persistido.
Batería y Radio Móvil (4G/5G) ✕ Alto drenaje de batería El sondeo constante impide que el módem celular entre en estado de reposo (RRC IDLE), manteniéndolo en modo de alta potencia (DCH). ✓ Conservación de batería El socket permanece inactivo con keep-alive liviano (ping/pong cada 30s), permitiendo al hardware móvil mantenerse en modo sleep.
Particionamiento y Seguridad ✕ Consultas continuas a BD Cada cliente consulta endpoints GET cada pocos segundos, incrementando la contención de base de datos. ✓ Aislamiento por Salas Suscripción al canal temático específico room:compra:{id}. Solo el comprador y el organizador autorizado reciben los frames.
Integración Clean Architecture Mezcla lectura periódica en controladores HTTP con lógica repetitiva de sincronización en el cliente móvil. ✓ Desacoplamiento Event-Driven La infraestructura de WebSockets actúa como un Transport Adapter que difunde eventos emitidos por el Aggregate de Dominio.
